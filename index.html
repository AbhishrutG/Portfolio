Why Sub-Workflows? Why Error Handling?
⏱️
Execution Timeout Problem
n8n has a 30-second execution limit. Scanning 36 queries × API calls takes 2–4 minutes. Solution: WF6 fires WF1 as a child webhook (async), returns 202 Accepted immediately so the parent doesn't timeout.
🔁
API Retry Logic
Google Places API occasionally rate-limits or returns 429. Each HTTP Request node is configured with retryOnFail: true, maxTries: 3, waitBetweenTries: 3000ms to handle transient failures automatically.
🛡️
Central Error Handler (WF-ERR)
Every workflow has errorWorkflow pointing to a central error handler. If any node fails, it logs the error, captures the stack trace, and sends an alert — so nothing fails silently in production.
🔄
Upsert Not Insert
PostgreSQL uses UPSERT on google_place_id as the unique key. If a shop is scanned twice across different searches, the row updates instead of creating a duplicate — database stays clean at all times.

How Email Tracking Works (Built From Scratch)
Open Tracking — Pixel Method

Each email contains a 1×1 transparent PNG served by an n8n webhook endpoint.

URL pattern: /track-open?lead_id=ABC123&email_num=3

When the email client loads the image, WF2C fires, finds the lead in Airtable, increments open count, adds +5 to score, and updates last_opened_at. No third-party service needed.

Click Tracking — Redirect Method

Links in emails don't go directly to the destination. They pass through a redirect webhook.

URL pattern: /track-click?lead_id=ABC123&url=https://...

WF2C intercepts the request, logs the click, adds +10 to score, updates click count in Airtable, then immediately redirects the user to the real destination — invisible to the reader.

Production Engineering

When It Breaks at 3 AM

A system isn't production-ready until it can recover without you. Every workflow in this system points to a central error handler. Here's exactly what happens when something goes wrong — and how the system heals itself.

🚨
WF-ERR — ALWAYS ACTIVE
Central Error Handler
errorWorkflow on ALL WFs

Every workflow — WF1 through WF9 — has errorWorkflow: WF-ERR set in its settings. When any node fails anywhere in the system, n8n automatically fires WF-ERR with the full error context before the execution dies.

📩 Instant Telegram Alert
Sends a message with: which workflow failed, which node, the error message, and a direct link to the failed execution in n8n.
📝 Error Log to PostgreSQL
Every error is written to the error_log table: timestamp, workflow name, node name, error type, input data snapshot.
🔁 Auto-Retry Logic
Google Places API nodes: 3 retries × 3s delay. Airtable nodes: 2 retries × 2s delay. Transient failures recover silently without any alert.
⏭ continueRegularOutput
Non-critical nodes use onError: continueRegularOutput — one bad lead doesn't stop the entire batch of 200.
📊
WF5 — DAILY CRON
Daily Health Report

Runs every morning at 7 AM. Queries all tables and sends a consolidated HTML report email showing the full system health from the past 24 hours.

Leads scanned (WF6) count
Leads enriched (WF7) qualified / rejected
Emails sent (WF9) first + followup
Errors in last 24h error count
Nurturing pipeline active / completed
🖥️
SRV-ALERT — CRON EVERY 5 MIN
Server Health Monitor

Monitors the Hetzner VPS hosting n8n every 5 minutes. Fires an alert if any threshold is breached — before the server actually crashes.

CPU > 85% for 3 consecutive checks → alert
RAM > 90% → alert + suggest restart
Disk > 80% → alert with cleanup suggestion
n8n process not responding → restart command
PostgreSQL not reachable → immediate alert
Failure Scenario: Google Places API goes down at 2 AM

1
WF6 fires, sends query to Google Places API
API returns 503. Node is configured with retryOnFail: true, maxTries: 3, waitBetweenTries: 3000ms
2

3
WF-ERR fires with full error context
Receives: workflow="WF6", node="Google Places API Search", error="503 Service Unavailable", execution_id, timestamp. Logs to PostgreSQL error_log table.

Right now WF6–WF9 (lead generation) and WF1–WF4 (partner nurturing) are two separate systems. The bridge automates the handoff — when a shop from WF9's outreach shows interest, it flows directly into WF1 without any manual step.

What the Bridge Workflow Does
1.Listens on a webhook triggered by WF9 when a shop clicks the registration link
2.Looks up the shop's record in verified_leads (PostgreSQL) to get business name, phone, category
3.Checks if this shop already exists in Airtable partner leads — prevents duplicates across both systems
4.If new: creates Airtable record, calls WF1's webhook with pre-filled shop data → nurturing starts automatically
5.Updates PostgreSQL record: pipeline_status = 'in_nurturing' — WF9 stops further outreach to this shop
