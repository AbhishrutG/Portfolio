Deep dive · Discover stage

Lead generation pipeline

Four workflows hand work to each other through PostgreSQL rather than calling each other directly. Each one runs on its own schedule, so a failure in one never blocks another.

STEP 1
Lead Generation Scanner
ON DEMAND · FORM

City + category in a form. Builds German search queries, calls the Google Places API (3 retries), removes chains and duplicates, normalizes, and upserts.

STEP 2
Lead Enrichment
DAILY · 06:00

Takes up to 200 raw leads, fetches each website, extracts an email, scores the lead, and keeps only those that pass the quality gate (score ≥ 2).

STEP 3
Sales Pipeline Manager
MON–FRI · 18:00

Collects new qualified leads, emails the team an HTML summary, and moves them to contacted in one batch update.

STEP 4
Lead Outreach
MON–FRI · 09:00

Sends German partnership emails: up to 10 first contacts and 10 follow-ups a day, at most 3 attempts per shop.

DATA HAND-OFF Scanner writes google_business_leads (raw)→ Enrichment marks enriched / rejected and upserts verified_leads→ Sales report and Outreach read verified_leads by pipeline_status

Production engineering

When it breaks at 3 AM

A system is not production-ready until it can recover without me. Here is what actually happens when something goes wrong, from a flaky API call to a server problem.

1 · FAILS
A step breaks

An API times out, a website does not answer, or one record has bad data.

2 · RECOVERS
Retry or skip

Flaky calls retry automatically. Non-critical steps carry on, so one bad lead never stops the batch.

3 · REPORTS
I am told

The central error handler emails which workflow and node failed, and why.

4 · RESUMES
Safe re-run

Progress lives in the database, so the next run continues cleanly with no duplicates.

Inside each workflow

  • Retries: the Google Places search retries 3 times (3 s apart); the website fetch in enrichment retries twice.
  • Keep going: up to 11 nodes in a single workflow continue on error, so one bad lead does not stop the other 199.
  • Validate and guard: bad input is rejected and logged; a lead already in nurturing is never started again.
  • Safe to repeat: upserts and contact history prevent duplicate rows and duplicate emails.
  • Caps and business hours: outreach is limited to 20 a day and only runs in business hours (Europe/Berlin).
  • Reply first: the nurturing entry webhook answers immediately and works afterwards, which fixed Cloudflare 524 timeouts.

Watching the whole system

  • Central error handler: an error trigger that emails the failure details to the team.
  • Daily monitoring report (08:00): lead counts plus every failed execution from the last 24 hours, pulled from the n8n API.
  • Server alerts: classified by severity. Critical goes to email and WhatsApp, warning to email, info is logged.
  • Health check: uptime is checked every 5 minutes, and the database is backed up daily.

IN PROGRESS · DESIGN & BUILD

Partner onboarding & document verification

A fully digital path from "Become a Partner" to an active, verified repair shop. Document requirements are decided by a configurable rules engine, so adding a requirement never means rebuilding the flow.

Try the requirement engine

The same rules from the spec, running live. Change the legal form and the checklist the partner sees changes with it.

Only asked where it changes the outcome (Einzelunternehmen, Other).

    PASS → VERIFIED

    Automated checks succeeded. No admin time spent.

    REVIEW → ADMIN_REVIEW

    Name/address mismatch, poor scan, low AI confidence. A human decides.

    ACTION REQUIRED

    Missing, expired or wrong document. The partner gets a clear explanation of what to fix.

    Designed for

    • NDA by version — accepted once per version; a new version re-prompts only existing partners.
    • Standard document statuses — uploaded, processing, verified, rejected, re-upload required, expired, not applicable.
    • Audit log for registration, uploads, automated results and every admin decision.

    Security by default

    • No public document URLs; admin-only access with role-based control.
    • Encryption in transit and at rest, access logging, retention and deletion rules.
    • Partner documents are never used for AI model training.
